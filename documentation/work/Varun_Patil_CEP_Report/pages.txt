ABSTRACT
Our Community Engagement Project resulted in Skill Bridge, a portal for student employment 
preparation and placement coordination. The team visited Khalsa College, Matunga, three times and 
gathered real student responses by manually distributing a Google Form. The project’s central concern 
is continuity: students should be able to move from finding an opportunity to taking action and receiving 
a response, while staff should have an organised view of the work requiring attention.
The application separates student, placement coordinator and administrator access. Its functions include 
profile management, opportunity discovery, explained matching, application tracking, workshops, 
feedback, guidance and research summaries. Coordinator actions update shared operational records, 
while administrative tools support configuration and data recovery. Individual survey responses are 
restricted, and public reporting uses aggregate information.
React, TypeScript, Vite, Tailwind CSS and Recharts form the frontend stack. The backend uses Express 
and SQLite. Matching is implemented as a deterministic scoring function that compares selected profile 
and listing attributes. Because it is a relevance aid rather than a predictive model, the interface also 
provides reasons and eligibility information. Authentication, server-side permissions, validation and 
relational constraints support the main workflows.
The latest recorded test run passed 157 checks across four suites, and both the production build and 
TypeScript verification succeeded. Fresh production serving, administrator login, an authorized update 
and logout were included in the checks. These results describe technical behaviour under the test 
conditions. They do not demonstrate live institutional adoption, performance under load or a change in 
employment outcomes. The project offers a usable foundation for coordinated placement support. 
Original survey totals, photographs, signed feedback and user-acceptance results are to be attached as 
the remaining fieldwork evidence.

1.2 Problem Statement 
Our project focuses on the practical gap between seeing an opportunity and receiving useful placement 
support. Students need relevant listings and visible progress; coordinators need structured records for 
decisions, training and guidance. The application was designed to support that whole sequence. Claims

1.3 Need for the Project 
The value of the project lies in making placement support understandable and traceable. A student 
should know what is available, what has been submitted and what response has been received. Staff 
should have an organised queue of work rather than relying on the student interface. The portal supports 
these needs without presenting a matching score as a guarantee of selection.

CHAPTER 3: PROPOSED SOLUTION 
3.1 Solution Overview 
The portal organises placement support around the people using it. Student actions create records, 
coordinator actions update their progress, and administrative tools protect the system’s configuration 
and data. The solution therefore combines an understandable interface with server-enforced control over 
what each account can do.
3.2 System Architecture 
The frontend communicates with the server through HTTP API calls. Session and role checks determine 
whether a request can proceed, then the server performs the necessary database operation. The interface 
updates from the returned result. This arrangement centralises authority and persistence instead of 
relying on browser-only state for important records.

Opportunity matching process 
Table 7: Matching score components
Component Points Implemented rule
Department 40 Awarded when the listing includes the profile department
Preferred role 25
Case-insensitive containment between a preferred role and 
listing title
Skill overlap Up to 20 Seven points per overlapping listed skill, capped at 20
Location 10 Preferred location matches, or the listing uses remote work
Academic cutoff 5 Entered percentage meets a detected two-digit percentage cutoff
The score is the sum of the awarded components, bounded between 0 and 100. Skill points are calculated 
as min(20, 7 × number of matching listing skills). A score of 75 or more is labelled High Fit; 50–74 is 
Moderate Fit; 30–49 is Partial Fit; lower scores are General Opportunity.
Text comparisons use case-insensitive containment, so the result depends on the terms entered in the 
profile and listing. The eligibility check detects a two-digit percentage cutoff and returns an eligibility 
caution where appropriate. It is not a complete eligibility parser. Students must review the original 
criteria even when the fit score is high.

CHAPTER 8: CONCLUSION AND FUTURE SCOPE 
8.1 Conclusion 
Skill Bridge provides a concrete outcome for the CEP work: a portal with distinct access, persistent 
records and verified local production behaviour. The project is grounded in three visits and real student 
data collection at Khalsa College. Its continuing value will depend on careful deployment, maintained 
information and documented feedback from users.
8.2 Key Findings 
The strongest technical lesson is the need to verify complete workflows rather than individual pages 
alone. Data integrity, account isolation and startup configuration affect every user journey. The project 
also requires a clear distinction between real survey evidence and controlled software tests when 
presenting results.
8.3 Recommendations 
Operational preparation should include a responsible administrator, a maintained backup schedule and 
a tested recovery process. The team should complete browser verification and obtain formal feedback. 
Survey totals, dates and signatures should be filled from verified records, and confidential response data 
should remain protected.
8.4 Future Enhancements 
The project can be extended through user-approved notifications, adaptable matching criteria and 
longer-term reporting. These additions should follow evidence of need. Future work should also 
measure accessibility and performance under realistic use, while retaining the existing boundaries 
around personal and survey data.

ANNEXURE H: USER MANUAL 
This guide summarises routine operation of Skill Bridge. The available controls depend on the account 
role. The final portal URL and operational contact are [To be added].
Student workflow 
1. Authenticate as a student and confirm that profile information is current.
2. Explore relevant opportunities and open their full details.
3. Compare the explanation with the original eligibility conditions.
4. Save or apply to the opportunity and monitor the stored application status.
5. Manage workshop participation through the available enrolment controls.
6. Use the support forms for feedback or guidance and end the session by logging out.
Coordinator workflow 
1. Log in to the placement coordinator account.
2. Manage the published opportunities and workshop details.
3. Inspect submitted applications and store decisions with any relevant feedback.
4. Use the enrolment roster for participation and attendance work.
5. Follow up on guidance and feedback queues.
6. Verify successful updates and close the session through logout.
Administrator workflow 
1. Access the administrative workspace using the assigned credentials.
2. Maintain system content and use the approved diagnostics.
3. Back up the database before sensitive maintenance.
4. Submit a suitable backup for restoration and inspect the returned outcome.
5. Restrict access to backup files and administrator credentials.
Local setup and production preparation 
Install a Node.js version compatible with the project dependencies and native SQLite support, then run 
npm install in the project folder.

PAGE 39
28
Use npm run dev for local development. The configured API and frontend addresses should be read 
from the terminal output.
Run npm run typecheck, npm run build and npm test before preparing a release.
For production, set NODE_ENV=production, a persistent DB_PATH and CLIENT_URL matching the 
actual website origin. Configure HTTPS and the intended reverse proxy.
Provision an administrator with explicit credentials using npm run admin:provision -- <username> 
<password>. Use protected credential handling in the deployment environment.
Run npm start after the build. Verify login, authorised changes and direct route refreshes on the actual 
host.
Use npm run backup:db for the database backup utility. Test recovery with a disposable copy before 
relying on a backup. Do not run demo reset commands against the real database.
If an operation fails 
When a request fails, inspect the current state first to avoid duplicate work. Check connectivity and 
permissions, and report continuing problems with the exact action and message. Do not include private 
records in a public error report.
