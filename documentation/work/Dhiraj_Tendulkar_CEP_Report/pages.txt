ABSTRACT
Skill Bridge is a community employment and skill matching portal developed as part of our Community 
Engagement Project at Khalsa College, Matunga. Our team completed three visits to the college and 
gathered real student inputs by manually circulating a Google Form. The project addresses the need to 
connect opportunity information, student interests, skill preparation and placement follow-up in a clear 
workflow. Its objective is to provide useful student services while giving coordinators a separate 
workspace for operational decisions.
The application provides profiles, opportunity browsing, explained matching, saved opportunities, 
applications, workshop enrolment, feedback and guidance requests. Coordinator functions include 
managing listings, reviewing applications, maintaining training records and responding to requests. 
Administrative functions cover protected content, diagnostic queries and backup restoration. Public 
research views use aggregate information, while access to individual survey responses is restricted.
The implementation uses React, TypeScript, Vite, Tailwind CSS and Recharts for the frontend, with an 
Express server and SQLite persistence. Matching is a deterministic weighted process based on profile 
and opportunity fields. It returns reasons for its assessment and does not predict the probability of 
employment. Server-side authorization, input validation and database constraints support reliable 
operation.
The latest recorded verification passed 157 automated checks across acceptance, workflow, lifecycle 
and production-serving suites. The TypeScript check and production build also passed. These results 
establish the tested technical behaviour, including fresh production startup and administrator operations. 
They do not establish a measured improvement in placement outcomes. The portal provides a practical 
basis for organised placement support; verified survey totals, signed user acceptance and measured 
institutional impact remain to be added to the final evidence record.

1.2 Problem Statement 
The problem addressed is the difficulty of connecting a student’s interests and skills with suitable 
placement opportunities while maintaining a clear record of applications and support needs. A listing 
alone does not explain whether a role fits a profile or what preparation is required. Coordinators also 
need a consistent way to review applications, manage workshops and respond to requests. Skill Bridge 
treats these activities as related parts of one process.
1.3 Need for the Project 
The need for the project is a clearer connection between information and action. Students should be 
able to save an opening, submit an application and later see its status. Training and guidance should 
also have a recorded follow-up rather than ending at a request. Separate permissions make the portal 
easier to demonstrate and help protect student-specific records during routine use.

CHAPTER 3: PROPOSED SOLUTION 
3.1 Solution Overview 
Skill Bridge provides connected workspaces for students, placement coordinators and administrators. 
Students discover opportunities and request support; coordinators review and respond; administrators 
maintain protected configuration and recovery tools. This structure turns the project requirements into 
a sequence of recorded actions, with the server controlling permissions.
3.2 System Architecture 
The browser runs the React interface and sends requests through the API service. Express receives these 
requests, resolves the session and checks the required role. Valid operations read or update SQLite, 
after which the result is returned to the interface. In production mode, Express also serves the built 
frontend assets. Environment configuration is loaded before database initialisation.

The design uses typed records for profiles, opportunities, applications, workshops and research 
responses. Relationships are stored in SQLite rather than reconstructed only in the interface. Validation 
checks input before persistence, while foreign keys and uniqueness constraints protect important 
relationships. The browser state presents these records but does not replace the database as the 
authoritative store.

administrator. Public access is limited to appropriate information and aggregate research. A student 
works with personal records; staff operate management functions. The server checks these boundaries 
even when an endpoint is called directly.

Table 7: Matching score components
Component Points Implemented rule
Department 40 Awarded when the listing includes the profile department
Preferred role 25
Case-insensitive containment between a preferred role and 
listing title
Skill overlap Up to 20 Seven points per overlapping listed skill, capped at 20
Location 10 Preferred location matches, or the listing uses remote work
Academic cutoff 5 Entered percentage meets a detected two-digit percentage cutoff
The score is the sum of the awarded components, bounded between 0 and 100. Skill points are calculated 
as min(20, 7 × number of matching listing skills). A score of 75 or more is labelled High Fit; 50–74 is 
Moderate Fit; 30–49 is Partial Fit; lower scores are General Opportunity.
Text comparisons use case-insensitive containment, so the result depends on the terms entered in the 
profile and listing. The eligibility check detects a two-digit percentage cutoff and returns an eligibility 
caution where appropriate. It is not a complete eligibility parser. Students must review the original 
criteria even when the fit score is high.

CHAPTER 5: PROJECT IMPLEMENTATION 
5.1 Development Methodology 
Development followed an iterative cycle of implementation, review and correction. The team 
maintained the existing application while addressing verified issues in permissions, restoration, 
validation and startup. Type checks, production builds and isolated tests were used after changes. This 
process allowed defects to be examined without resetting the real project database.
5.2 Module-wise Implementation 
The source is organised into React pages, reusable components, shared context, API services and server 
modules. AppContext coordinates session and data refreshes. The API service sends authenticated 
requests, and Express performs role checks and validation. SQLite retains the resulting records. This 
structure implements the proposed separation between student actions, coordinator decisions and 
administrative maintenance.

Authentication and data integrity 
Passwords are hashed with scrypt and a salt. Session tokens are carried in an HttpOnly cookie, and 
protected routes verify the session and role. Public registration is restricted to the student role. Database 
uniqueness constraints help prevent duplicate applications and enrolments. Restore operations validate 
supported content and relationships before transactional updates.
Research summaries 
The reporting process groups responses by the requested filters and computes counts, distributions and 
rating summaries. Non-rated responses such as “Have not attended” are not treated as numeric 
satisfaction scores. Public reporting uses aggregate endpoints; individual responses are limited to 
authorized staff. The actual field-response totals and numerical findings are [To be added].
5.3 User Interface Solution 
The interface gives students and coordinators different navigation and actions. Students see personal 
application and support tools, while coordinators receive management views. Forms and status 
messages help users understand what happened after an action. Responsive styling is implemented, but 
a complete interactive mobile and accessibility walkthrough remains a separate verification item.

The technical work establishes differentiated access, persistent workflows and a passing automated test 
baseline. Final photographs, signed records and user-acceptance evidence will complete the submission 
record.
8.2 Key Findings 
The implementation shows that permission checks, validation and database relationships are central to 
a reliable portal. A successful build alone is insufficient; startup and workflow tests exposed problems 
that required correction. Matching explanations are also important because a numerical score needs 
context. Field-response findings must be drawn from the original response export.
8.3 Recommendations 
Before institutional use, assign an operational owner, verify the deployment configuration and complete 
a student–coordinator browser walkthrough. Keep backups and test recovery periodically. Add the 
original Google Form summary, visit dates and signed attachments to the report. Review privacy 
requirements before publishing any research output.
8.4 Future Enhancements 
Possible future work includes configurable matching rules, opt-in reminders and richer follow-up 
reporting. These would require additional implementation and evaluation. Accessibility testing and 
measured performance on the deployment host would also improve confidence. None of these proposed 
extensions is presented as an existing feature.

ANNEXURE H: USER MANUAL 
This manual follows the principal tasks of each role. Use the account provided for the intended role and 
keep credentials private. The actual hosting URL is [To be added].
Student workflow 
1. Sign in and review your profile, including department, skills and preferred roles.
2. Open opportunities, apply relevant filters and read the listing details.
3. Review matching reasons and the original eligibility requirements before applying.
4. Save an opening for later or submit one application; check its status in your workspace.
5. Use the workshop section to enrol, review participation or cancel where permitted.
6. Submit feedback or a guidance request and return to view the response. Sign out when finished.
Coordinator workflow 
1. Sign in with a placement coordinator account.
2. Maintain opportunities and workshop records through the management views.
3. Review student applications and record decisions or feedback.
4. Use workshop rosters to maintain the available participation and attendance information.
5. Respond to feedback and guidance requests; review research records only for authorised work.
6. Confirm save messages and revisit the record if a request fails.
Administrator workflow 
1. Use an explicitly provisioned administrator account.
2. Maintain protected content and run only the approved diagnostic queries.
3. Export a backup before a sensitive maintenance operation.
4. Restore only a validated backup and check the resulting records.
5. Keep database backups and credentials in protected storage.
Local setup and production preparation 
Install a Node.js version compatible with the project dependencies and native SQLite support, then run 
npm install in the project folder.

Use npm run dev for local development. The configured API and frontend addresses should be read 
from the terminal output.
Run npm run typecheck, npm run build and npm test before preparing a release.
For production, set NODE_ENV=production, a persistent DB_PATH and CLIENT_URL matching the 
actual website origin. Configure HTTPS and the intended reverse proxy.
Provision an administrator with explicit credentials using npm run admin:provision -- <username> 
<password>. Use protected credential handling in the deployment environment.
Run npm start after the build. Verify login, authorised changes and direct route refreshes on the actual 
host.
Use npm run backup:db for the database backup utility. Test recovery with a disposable copy before 
relying on a backup. Do not run demo reset commands against the real database.
If an operation fails 
Read the displayed error and check the current record before repeating a submission. Confirm that the 
server is running and the account has the required role. For repeated failures, record the action and error 
for the administrator without sharing private student data.
