ABSTRACT
Skill Bridge was developed to connect student placement activities with coordinator follow-up through 
a shared web application. The project formed part of our CEP work at Khalsa College, Matunga, where 
all three team visits took place. Student information was gathered manually through a circulated Google 
Form. The purpose was to support a more connected process for opportunity discovery, preparation, 
applications and requests for assistance, while keeping responsibilities and access distinct.
The solution contains student profiles, opportunity listings, saved records, applications, workshop 
participation, feedback and guidance. Coordinators manage the operational queues and record 
decisions. Administrators handle protected system documents, approved diagnostics and backup 
restoration. Research information is presented publicly through summaries, with individual respondent 
records limited to authorized staff. Persistent records allow actions and decisions to be retrieved across 
sessions.
The technical structure consists of a React and TypeScript frontend, an Express API and a SQLite 
database. Vite prepares the frontend build, Tailwind CSS provides styling and Recharts supports charts. 
Matching uses fixed weighted comparisons rather than machine learning. It provides reasons and 
eligibility cautions so that students can interpret the result instead of treating it as a hiring prediction.
The final recorded verification passed 37 acceptance checks, 97 workflow and security checks, 14 
lifecycle checks and 9 production-serving checks. The build and TypeScript checks also passed. This 
evidence supports the tested local operation of the portal, including production startup and 
administration. It does not replace field-based user acceptance or demonstrate improved placement 
rates. The project delivers a practical system and a documented technical baseline. Verified survey 
analysis, visit evidence and formal acceptance records remain necessary supporting material for the 
final submission.

1.2 Problem Statement 
The central design problem is keeping opportunity information, student preferences and coordinator 
decisions connected. When these records are handled separately, a student can struggle to identify a 
suitable opening or understand an application’s progress. The proposed portal gives each participant an 
appropriate workspace and records the interaction between them. Verified numerical findings from the 
collected Google Form responses are [To be added].
1.3 Need for the Project 
Skill Bridge is needed as a practical link between placement information and the actions taken on it. 
Searchable listings are useful only when students can act on them and coordinators can respond. 
Bringing applications, workshops and guidance into the same database provides continuity. The project 
also provides a setting in which role separation and accountable record keeping can be demonstrated.

CHAPTER 3: PROPOSED SOLUTION 
3.1 Solution Overview 
The proposed solution uses one application with distinct access levels. A student’s account supports 
personal actions, while staff accounts support coordination and administration. Shared records connect 
the interfaces without giving every user the same permissions. This design is central to both the project 
demonstration and its intended operational use.
3.2 System Architecture 
A client–server architecture separates presentation from data operations. React renders the screens, an 
API service sends requests, and Express performs validation and permission checks. SQLite stores the 
resulting records. Production serving combines the compiled frontend and API behind the server, while 
configuration is established before storage is opened.

Table 7: Matching score components
Component Points Implemented rule
Department 40 Awarded when the listing includes the profile department
Preferred role 25
Case-insensitive containment between a preferred role and

Skill overlap Up to 20 Seven points per overlapping listed skill, capped at 20

The score is the sum of the awarded components, bounded between 0 and 100. Skill points are calculated 
as min(20, 7 × number of matching listing skills). A score of 75 or more is labelled High Fit; 50–74 is 
Moderate Fit; 30–49 is Partial Fit; lower scores are General Opportunity.
Text comparisons use case-insensitive containment, so the result depends on the terms entered in the 
profile and listing. The eligibility check detects a two-digit percentage cutoff and returns an eligibility 
caution where appropriate. It is not a complete eligibility parser. Students must review the original 
criteria even when the fit score is high.

Our development method relied on small, verifiable changes to the existing project. Reviews identified

Authentication and data integrity 
Passwords are hashed with scrypt and a salt. Session tokens are carried in an HttpOnly cookie, and

supported content and relationships before transactional updates.

rating summaries. Non-rated responses such as “Have not attended” are not treated as numeric 
satisfaction scores. Public reporting uses aggregate endpoints; individual responses are limited to

without using staff management screens. Coordinators can review and update operational work through 
dedicated controls. Responsive styles are present, although this report does not claim a completed 
evaluation on every device or assistive technology.

ANNEXURE H: USER MANUAL 
Use this guide to follow the main student and staff activities. A user must sign in with the appropriate 
account before performing protected actions. The live website address is [To be added].
Student workflow 
1. Enter the student workspace and complete the profile fields used for matching.
2. Find a listing through browsing or filtering and inspect its requirements.
3. Check the match reasons without treating the score as a selection guarantee.
4. Submit an application once and follow its recorded status.
5. Review workshop details before enrolling or cancelling participation.
6. Record a feedback or guidance request when needed, then sign out securely.
Coordinator workflow 
1. Use coordinator credentials to access the operational dashboard.
2. Keep listings and workshops current, including dates and capacity.
3. Review the application records and provide the relevant decision.
4. Maintain workshop participation and attendance from the available roster.
5. Respond to student support requests and use restricted research views responsibly.
6. Treat an error message as an unsuccessful action until the record is verified.
Administrator workflow 
1. Authenticate with the administrator account created for the deployment.
2. Use protected content and diagnostic tools only for necessary maintenance.
3. Take a backup before operations that could affect stored data.
4. Check a restoration result and the linked operational records.
5. Store backups securely and log out after administration.
Local setup and production preparation 
Install a Node.js version compatible with the project dependencies and native SQLite support, then run 
npm install in the project folder.

PAGE 39
28
Use npm run dev for local development. The configured API and frontend addresses should be read 
from the terminal output.
Run npm run typecheck, npm run build and npm test before preparing a release.
For production, set NODE_ENV=production, a persistent DB_PATH and CLIENT_URL matching the 
actual website origin. Configure HTTPS and the intended reverse proxy.
Provision an administrator with explicit credentials using npm run admin:provision -- <username> 
<password>. Use protected credential handling in the deployment environment.
Run npm start after the build. Verify login, authorised changes and direct route refreshes on the actual 
host.
Use npm run backup:db for the database backup utility. Test recovery with a disposable copy before 
relying on a backup. Do not run demo reset commands against the real database.
If an operation fails 
An error should be investigated rather than treated as a successful save. Recheck the record, connection 
and account permissions. Report reproducible failures to the administrator with the relevant steps, 
keeping personal information private.
