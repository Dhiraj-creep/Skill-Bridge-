ABSTRACT
This Community Engagement Project presents Skill Bridge, a web portal intended to make placement 
support easier to follow for students and coordinators. The fieldwork was carried out through three 
visits to Khalsa College, Matunga. We collected genuine responses by manually sharing a Google Form 
among students. The work focuses on the connection between understanding student needs and 
providing a system through which opportunities, applications, training and guidance can be managed.
Students use a personal workspace to maintain profile information, explore openings, read matching 
explanations, apply for opportunities and enrol in workshops. They can also submit feedback and 
request guidance. Coordinators receive separate management views for reviewing applications and 
handling operational work. Administrators maintain protected configuration and recovery functions. 
The access model is enforced through server checks rather than interface visibility alone.
The portal uses React and TypeScript, supported by Vite, Tailwind CSS and Recharts. Express provides 
the API, and SQLite stores related records. A rule-based scoring process compares department, role 
preference, skills, location and a detected academic cutoff. The output is advisory: it explains relevance 
without claiming to determine employer selection.
Technical validation included compilation, isolated workflows, database lifecycle checks and 
production serving. The latest recorded run passed 157 automated checks, along with TypeScript and 
the production build. Lint completed with warnings. The results show that the tested functions operate 
as expected, but direct user acceptance and live-host verification remain separate activities. Skill Bridge 
offers a structured support mechanism aligned with learning and employment preparation. Confirmed 
field-response statistics, signed feedback and evidence of organisational adoption are to be added from 
the original records.

1.2 Problem Statement 
A placement-support system must do more than display vacancies. Students need to understand 
relevance, eligibility and the next action, while coordinators need visibility into applications and 
training participation. The project therefore addresses the lack of a connected workflow between 
opportunity discovery, skill preparation and follow-up. The statement describes the problem our

coordinators handle operational decisions, and administrators maintain the system. This separation is 
important for both usability and data protection. Any measured reduction in administrative effort 
remains to be established through a live evaluation.

CHAPTER 3: PROPOSED SOLUTION 
3.1 Solution Overview 
The solution is a web portal that gives each role the tools needed for its work. Students manage their 
own placement activities, coordinators operate shared queues, and administrators handle system 
maintenance. A common API and database connect these views so that a recorded decision can be 
retrieved in the appropriate workspace.
3.2 System Architecture 
The architecture has three main layers: the React user interface, the Express application server and 
SQLite storage. The interface does not grant authority by itself. Each protected request is checked on 
the server before database access. Configuration controls the port, database location and allowed 
origins; the production server can also deliver the compiled frontend.

Table 7: Matching score components
Component Points Implemented rule
Department 40 Awarded when the listing includes the profile department
Preferred role 25
Case-insensitive containment between a preferred role and 
listing title
Skill overlap Up to 20 Seven points per overlapping listed skill, capped at 20
Location 10 Preferred location matches, or the listing uses remote work
Academic cutoff 5 Entered percentage meets a detected two-digit percentage cutoff
The score is the sum of the awarded components, bounded between 0 and 100. Skill points are calculated 
as min(20, 7 × number of matching listing skills). A score of 75 or more is labelled High Fit; 50–74 is 
Moderate Fit; 30–49 is Partial Fit; lower scores are General Opportunity.
Text comparisons use case-insensitive containment, so the result depends on the terms entered in the 
profile and listing. The eligibility check detects a two-digit percentage cutoff and returns an eligibility 
caution where appropriate. It is not a complete eligibility parser. Students must review the original 
criteria even when the fit score is high.

8.1 Conclusion

8.3 Recommendations 
The next practical steps are controlled deployment, user acceptance and completion of the evidence 
record. Staff should agree who maintains listings, responds to requests and manages backups. Public 
reports should remain aggregate, with individual responses restricted. Field photographs and signed 
forms should be attached before submission.
8.4 Future Enhancements 
Future development could add carefully controlled notifications, more configurable matching and 
reporting across longer periods. Any extension should preserve privacy and be evaluated with users. A 
documented accessibility review and host-level performance study would complement the existing 
technical tests.

ANNEXURE H: USER MANUAL 
The instructions below describe how to use the completed workflows. Access depends on the signed￾in account. The deployment address and support contact are [To be added].
Student workflow 
1. Start by signing in to the student account and checking the accuracy of profile details.
2. Browse the opportunities and use filters to narrow the list.
3. Read the fit explanation as an aid, then verify the stated eligibility and deadline.
4. Apply to a selected opening or save it; return to the application record for updates.
5. Enrol in an appropriate workshop if capacity is available.
6. Use feedback or guidance for additional support, and log out after the session.
Coordinator workflow 
1. Open the coordinator workspace using the assigned account.
2. Create or update opportunity and training information after checking its accuracy.
3. Work through the application queue and save the appropriate decision.
4. Review enrolments and attendance from the workshop roster.
5. Handle guidance and feedback requests through their management screens.
6. Check the returned status after each update and sign out when the work is complete.
Administrator workflow 
1. Sign in through the provisioned administrative account.
2. Review configuration and use the registered diagnostics for maintenance.
3. Create a backup before performing sensitive changes.
4. Use the restore control with an appropriate backup file and confirm the result.
5. Protect the backup files and avoid sharing administrative credentials.
Local setup and production preparation 
Install a Node.js version compatible with the project dependencies and native SQLite support, then run 
npm install in the project folder.

28
Use npm run dev for local development. The configured API and frontend addresses should be read 
from the terminal output.
Run npm run typecheck, npm run build and npm test before preparing a release.
